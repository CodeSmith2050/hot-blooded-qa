# 热血问答 - AI 模块规划（未来规划）

> 本文档为 AI 功能模块的独立规划，**不与现有 PRD / 功能列表混合**，作为未来版本演进的蓝图。
> 当前版本（V1）以传统问卷 CRUD 为核心，AI 模块（V2+）在此基础上叠加。
>
> **创建时间**：2026-07-16
> **版本**：v0.1（草案）
> **状态**：🔵 未来规划（未启动）

## 一、AI 模块定位

### 1.1 核心价值

从「手动拖拽式问卷创建」升级为「多模态 AI 协作式问卷创建」，将创建问卷的时间从「30 分钟～2 小时」缩短至「30 秒～3 分钟」，大幅降低用户门槛。

### 1.2 设计原则

1. **并行子系统**：AI 模块作为独立子系统叠加，与现有问卷 CRUD 解耦，不侵入 V1 代码
2. **渐进式引入**：从文本主题生成（最简路径）起步，逐步扩展多模态和对话式能力
3. **输出标准化**：AI 输出统一为 V1 已有的 `IQuestion[]` 结构，现有编辑器、存储、渲染直接复用
4. **用户可控**：AI 生成结果仅作为草稿，用户必须确认/编辑后才可发布，AI 不直接发布
5. **全链路可追溯**：每次 AI 生成都记录输入、输出、token 消耗、耗时，便于审计与优化

### 3.2 关键设计决策

| 决策点 | 方案 | 理由 |
|-------|------|------|
| LLM Provider 抽象 | 统一 `BaseProvider` 接口 + 多 Provider 实现 | 避免厂商锁定，支持灵活切换与降级 |
| 生成模式 | 异步任务队列 + SSE 流式推送 | AI 生成 10s~60s，同步请求超时；流式体验更好 |
| 输出规范 | 强制 JSON Schema + 后端校验 + 自动补缺 | 防止 LLM 输出漂移，保证前端可直接渲染 |
| 与 V1 集成方式 | AI 输出 → IQuestion[] → 直接存入 Questionnaire | 复用 V1 全部编辑器、存储、渲染能力 |
| 对话历史存储 | 独立 AIMessage 集合，与问卷 ID 关联 | 支持多轮上下文，不污染问卷数据 |
| 配额管理 | 按用户维度限流 + 每日 token 上限 | 防止滥用，控制成本 |

## 四、数据模型设计（新增）

### 4.1 AIGenerationTask（AI 生成任务）

| 字段 | 类型 | 必填 | 说明 |
|-----|------|------|-----|
| `_id` | ObjectId | 是 | 任务 ID |

| `inputType` | enum | 是 | `text` / `audio` / `image` / `document` |
| `inputData` | Mixed | 是 | 输入数据（文本内容 / 文件路径 + 元数据） |
| `status` | enum | 是 | `pending` / `processing` / `completed` / `failed` / `cancelled` |
| `result` | Mixed | 否 | 生成结果（IQuestion[] 或分析结论） |
| `questionnaireId` | ObjectId | 否 | 关联的问卷 ID（生成后可创建/更新问卷） |
| `provider` | String | 是 | 使用的 AI 厂商（如 `qwen`、`openai`） |
| `model` | String | 是 | 使用的模型名（如 `qwen-plus`） |
| `promptTokens` | Number | 否 | 输入 token 数 |
| `completionTokens` | Number | 否 | 输出 token 数 |
| `totalTokens` | Number | 否 | 总 token 数 |
| `cost` | Number | 否 | 预估费用（元） |
| `durationMs` | Number | 否 | 生成耗时（毫秒） |
| `errorMessage` | String | 否 | 失败原因 |
| `retryCount` | Number | 否 | 重试次数，默认 0 |
| `createdAt` | Date | 是 | 创建时间 |
| `completedAt` | Date | 否 | 完成时间 |

**索引**：`userId`、`status`、`createdAt`、`questionnaireId`

| 字段 | 类型 | 必填 | 说明 |

| `taskId` | ObjectId | 否 | 关联的生成任务 ID |
| `createdAt` | Date | 是 | 创建时间 |

**索引**：`sessionId`、`userId`、`questionnaireId`、`createdAt`

### 4.3 AISettings（AI 配置，管理员 + 用户级）

| 字段 | 类型 | 必填 | 说明 |
|-----|------|------|-----|
| `_id` | ObjectId | 是 | 配置 ID |

| `userId` | ObjectId | 否 | 用户级配置时的用户 ID |

| `customPrompt` | String | 否 | 自定义系统提示词 |
| `apiKeys` | Mixed | 否 | 各 Provider 的 API Key（加密存储） |
| `updatedAt` | Date | 是 | 更新时间 |

### 4.4 Question 模型扩展（aiMeta 字段，V1 不影响）

在现有 `IQuestion` 接口中**可选添加** `aiMeta` 字段（V1 无需改动，V2 渐进式增加）：

```typescript
interface IAIMeta {
  generatedBy: 'human' | 'ai' | 'ai_human_edited';  // 生成来源
  aiModel?: string;        // 哪个模型生成的
  aiTaskId?: string;       // 关联的生成任务
  generatedAt?: Date;      // AI 生成时间
  editedByHuman?: boolean; // 是否经过人工修改
}
```

> **注意**：此字段为纯扩展，V1 代码完全不受影响，默认值为 `generatedBy: 'human'`。

### 6.2 核心交互流程

**流程 1：一句话生成问卷**
```
用户点击"AI 创建"
  → 弹出 AIGeneratePanel
  → 选择"文字主题"Tab
  → 输入"献血后恢复满意度调查，8-10题"
  → 点击"生成"
  → 显示流式预览（题目逐个出现）
  → 生成完成，底部按钮：
     [ 直接创建问卷 ] [ 继续对话调整 ] [ 重新生成 ]
  → 用户确认 → 跳转到编辑器，AI 生成的题目可继续编辑
```

**流程 2：语音生成**
```
用户点击"AI 创建"
  → 选择"语音"Tab
  → 按住说话按钮 → 录音中（波形动画）
  → 松开 → 显示识别中的文字
  → 识别完成 → 可编辑文字
  → 点击"生成问卷"
  → 流式预览
  → 确认创建
```

**流程 3：对话式调整**
```
用户在编辑器中 → 点击右侧"AI 助手"面板
  → AI: "我可以帮你调整问卷，说说你想改什么？"
  → 用户: "把第3题改成评分题"
  → AI 调整 → 流式输出更新后的问卷
  → 用户: "再加两道关于饮食习惯的题"
  → ...（多轮）
  → 用户点击"应用更改" → 问卷更新
```

## 八、技术选型建议

### 8.1 LLM Provider（国内优先，双 Provider 兜底）

| 厂商 | 模型 | 优势 | 适用场景 |
|-----|------|------|---------|
| 阿里通义千问 | qwen-plus / qwen-max | 中文能力强、价格适中、多模态支持好 | 主力 Provider |
| 智谱 AI | glm-4-plus | 清华系、代码能力强、支持工具调用 | 备选 Provider |
| DeepSeek | deepseek-v3 | 价格极低、推理能力强 | 量大时成本优化 |
| OpenAI | gpt-4o / gpt-4o-mini | 能力最强但需合规评估 | 仅在有海外部署场景时考虑 |

**建议**：默认使用通义千问（中文场景最优），同时接入智谱作为降级备选。

### 8.2 关键依赖库

| 功能 | 推荐库 | 说明 |
|-----|-------|------|
| 任务队列 | BullMQ | Redis 驱动，支持优先级、延迟、重试，Node 生态首选 |
| SSE | `express` 原生 + `eventsource-parser` | 轻量，无需引入 WebSocket |
| 语音录制 | `recordrtc` 或浏览器 MediaRecorder API | 前端录音，输出 WAV/MP3 |
| ASR | 通义千问语音识别 / 阿里云一句话识别 | 国内服务，合规 |
| 文档解析 | `pdf-parse` / `mammoth` | 后端解析 PDF/Word，提取文本 |
| Prompt 管理 | 纯 TS 模板字符串（初期）→ 后续引入 `@langchain/core` | 初期不要过度设计 |
| Token 计量 | `tiktoken` (OpenAI) / 厂商自带统计 | 计量需与 Provider 对应 |

### 8.3 新增基础设施

| 组件 | 用途 | 部署方式 |
|-----|------|---------|
| Redis | BullMQ 任务队列 + 缓存 + 限流计数 | Docker Compose 中新增 redis 服务 |
| 对象存储（可选） | 语音/图片/文档临时文件存储 | 初期可用本地磁盘，后期接 OSS/COS |

## 十、风险与挑战

| 风险 | 等级 | 应对策略 |
|-----|------|---------|
| LLM 输出不稳定，题目格式错乱 | 高 | 强制 JSON Schema + 后端严格校验 + 自动补缺；失败自动重试 2 次 |
| 生成质量参差不齐，用户满意度低 | 高 | 初期 prompt 深度调优 + 行业知识库增强；提供"重新生成""换一题"按钮 |
| 成本失控（用户滥用） | 中 | 用户级日/月配额 + 管理员全局配额；异常调用自动限流 |
| 数据合规（献血相关医疗数据） | 高 | 优先选择国内合规厂商；用户输入脱敏；不将答卷数据送 LLM（仅分析时需用户确认） |
| 语音/图片识别准确率 | 中 | 国内 ASR/OCR 服务已较成熟；前端允许用户编辑识别后文字再生成 |
| Redis 引入增加部署复杂度 | 低 | Docker Compose 中加一个 redis 服务即可，运维成本可控 |

## 十一、与 V1 功能的集成点汇总

> 以下为 AI 模块与现有 V1 系统的所有接触点，V1 代码**无需预先修改**，AI 模块主动适配。

| 集成点 | V1 侧 | AI 侧 | 方式 |
