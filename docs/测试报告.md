## 五、测试发现的问题

### BUG-001：统计接口路由顺序错误（已修复 ✅）

**现象**：`GET /api/answers/statistics/:questionnaireId` 始终返回 404。

**根因**：[backend/src/routes/answer.ts](../backend/src/routes/answer.ts) 中路由定义顺序为：

```
router.get('/:questionnaireId', ...)              // 第1个
router.get('/:questionnaireId/:answerId', ...)    // 第2个
router.get('/statistics/:questionnaireId', ...)   // 第3个
```

Express 按定义顺序匹配，`/statistics/xxx` 会被第 2 条路由 `/:questionnaireId/:answerId` 先匹配，使 `questionnaireId='statistics'`、`answerId=xxx`，调用 `getAnswerDetail` 而非 `getStatistics`，因找不到该 answer 返回 404。

**影响**：功能列表 D-003（基础统计）实际无法正常工作，前端 [StatisticsPage.tsx](../frontend/src/pages/Admin/StatisticsPage.tsx) 的统计数据加载会失败。

**修复方案**：将 `statistics` 路由定义移至 `/:questionnaireId` 与 `/:questionnaireId/:answerId` 之前：

```
router.get('/statistics/:questionnaireId', ...)   // 移到最前
router.get('/:questionnaireId', ...)
router.get('/:questionnaireId/:answerId', ...)
```

**修复状态**：✅ 已修复
- 修复分支：`bugfix/fix-001-statistics-route-0717`
- 修复提交：`008f899 fix(answers): 修复统计接口路由顺序错误导致 404 (BUG-001)`
- 修复日期：2026-07-17
- 验证结果：66 个单元测试全部通过，answerController 覆盖率从 61.01% 提升至 83.05%
- 已按规则从项目记忆「已知缺陷与待修复清单」移除，归档至「已修复历史」

### BUG-002：F-006/S-005 引入后破坏现有 D-001~D-005 连续提交测试（已修复 ✅）

**现象**：批次 3 引入 F-006 防重复提交（同 IP+问卷 10s 窗口）和 S-005 限流（同 IP 5 次/分钟）后，answer.test.ts 中 10 个用例失败（D-001~D-005 模拟"多用户提交"的场景，但 supertest 默认所有请求来自同一 IP，被风控规则拦截）。

**根因**：
1. supertest 默认所有请求来自同一 IP（::ffff:127.0.0.1）
2. `rateLimit` 中间件是模块级单例 Map，测试间不重置
3. `app.ts` 未设置 `app.set('trust proxy')`，导致 `req.ip` 始终为 127.0.0.1，rateLimit 默认 keyGenerator 失效

**影响范围**：仅影响测试，不影响生产功能。F-006/S-005/S-004 真实功能符合预期。

**修复方案**：
1. 在 [answer.ts](../backend/src/routes/answer.ts) 中为 rateLimit 添加 `keyGenerator: extractClientIp`，显式解析 `X-Forwarded-For` 头作为限流 key（兼容未配置 trust proxy 的场景）
2. 在 [answer.test.ts](../backend/test/answer.test.ts) 中添加 `submitAnswer` 辅助函数，为每次提交分配唯一 X-Forwarded-For IP（第三段自增 `10.0.${counter++}.2`，确保脱敏后仍唯一），模拟不同用户提交
3. F-006/S-005/S-004 专项测试显式使用相同 IP 验证风控规则本身

**修复状态**：✅ 已修复
- 修复分支：`feature/batch3-anti-spam-0717`（与功能开发同分支）
- 修复日期：2026-07-17
- 验证结果：86 个单元测试全部通过，answerController 覆盖率从 83.05% 提升至 87.7%，rateLimit.ts 覆盖率 79.31%
- 已按规则从项目记忆「已知缺陷与待修复清单」移除，归档至「已修复历史」

### BUG-003：微信 JS-SDK 签名算法参数顺序错误 + 测试票面数据错误（已修复 ✅）

**现象**：批次 6 F-004 初版 `generateSignature` 实现中，签名拼接参数顺序与微信官方要求的字典序不一致；同时 [wx.test.ts](../backend/test/wx.test.ts) 中使用非官方示例数据作为票面，无法验证签名算法正确性。

**根因**：
1. 微信官方签名算法要求参数按字段名 ASCII 字典序排列：`jsapi_ticket → noncestr → timestamp → url`
2. 初版实现拼接顺序与官方要求存在偏差
3. 测试用例未使用微信官方文档示例数据，无法对齐权威值

**影响**：F-004 微信 JS-SDK 签名计算错误会导致 `wx.config` 失败，前端降级为仅 UA 检测模式，无法调用微信分享等 JS 接口。

**修复方案**：
1. [wxController.ts](../backend/src/controllers/wxController.ts) `generateSignature` 严格按字典序拼接 `jsapi_ticket=${ticket}&noncestr=${nonceStr}&timestamp=${timestamp}&url=${url}`
2. [wx.test.ts](../backend/test/wx.test.ts) 签名算法测试改用微信官方文档示例数据，对齐权威 SHA1 签名值 `0f9de62fce790f9a083d5c99e95740ceb90c27ed`

**修复状态**：✅ 已修复
- 修复分支：`feature/batch6-matrix-wechat-restored-0717`（与功能开发同分支）
- 修复日期：2026-07-17
- 验证结果：8 个 F-004 测试用例全部通过，签名算法对齐微信官方示例数据
- 已按规则从项目记忆「已知缺陷与待修复清单」移除，归档至「已修复历史」
